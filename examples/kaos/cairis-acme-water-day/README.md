# ACME Water: Day (CAIRIS)

ACME Water, the CAIRIS exemplar of a water company's SCADA (its telemetry, ICT and plant, by day and by night), environment **Day**, as lib's CAIRIS importer reads it (goal-controller#192): one KAOS model per environment (D2).

Source: `examples/exemplars/ACME_Water/ACME_Water.xml` in [cairis-platform/cairis](https://github.com/cairis-platform/cairis) at `44cc57d` (Apache 2.0; the file's licence header is kept in lib's copy, `packages/lib/test/importers/fixtures/cairis/ACME_Water.xml`, with CAIRIS's LICENSE). See S. Faily, *Designing Usable and Secure Software with IRIS and CAIRIS*, Springer 2018.

- `cairis-acme-water-day.txt`: the model, the file read for this environment. It has 78 goals, 24 requirements, 1 domain property, 21 obstacles, 10 agents (CAIRIS's roles), with 32 goal refinements, 11 obstacle refinements, 11 obstructions, 41 responsibility assignments. It opens in kaosprop's mode. There is no CAIRIS writer (D4 of #192), so the file is the source and the model is its JSON.
- Values are CAIRIS's, verbatim (D1): a goal's category is its `Type` and its priority its `Priority`, an obstacle's category its `Category`, a domain property's type its `Kind`. The model records the `cairis` vocabulary profile (`diagram.customProperties.vocabulary`), so these values are checked against CAIRIS's enumerations (`goals.dtd`), not the `kaos` dialect's. Without the profile, nearly every goal, obstacle and domain property would be a Problem: `High`, not `high`; `Vulnerability`, not one of TSE'00's five.
- A requirement is a leaf goal (D3), with CAIRIS's `type` and `priority` as `RequirementType` and `RequirementPriority`. It is assigned to the role a manual association names. Requirements, domain properties and roles belong to the project, not to an environment: each is in the environments whose associations (or, for a requirement, whose asset or environment) situate it, and in every environment when nothing does.
- Nothing is left out silently: 12 association(s) with no KAOS link (a task, a use case, a vulnerability, a response, a role dependency) are kept as written in the diagram's `cairisUnsupported`, and the import says each. The rest of the file (assets, threats, vulnerabilities, risks, personas, use cases, countermeasures, …) is counted by the import, not read.
- `cairis-acme-water-day.expected.csv`: the **field cross-check** (goal-controller#192). Its 20 declared obstacles carry a probability in the file (CAIRIS's own, with its rationale). The 21st is a use case's exception, which CAIRIS turns into an obstacle on import; it has no probability, and is 0 in both. Each row has two values: CAIRIS's `obstacleProbability`, run in Docker by `scripts/kaos-stress/cairis-oracle.sh`, and kaosprop's RE'12 value. Where they differ, the row says why: CAIRIS sums an OR where RE'12 takes a noisy-or (Unscanned media 0.9 vs 0.82, Undetected malicious traffic 0.5 vs 0.46), and CAIRIS's AND product starts from 0 (Surplus equipment 0 vs 0.48). No source prints these numbers, so this is a cross-check, not a published oracle.
